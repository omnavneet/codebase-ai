# Product evaluation

Run `python -m eval.run --suite product` from the repository root with the app, MailHog, and a working model provider. The suite uploads a two-file synthetic repository, waits for indexing, and makes six requests. It exercises the synchronous endpoints and removes its temporary project. It requires neither benchmark repository downloads nor a second model to judge each answer.

`product_results.json` records each answer, latency, optional token usage and cost, evaluation pass flags, and request failures. Chat and Deep answer the same receipt-format and missing-provider questions. Compare their rows for `shared_cases` directly. A separate chat turn asks about a negative number without repeating the symbol and reuses the first conversation. Debug receives a traceback and is checked for the exception and source span. Mode aggregates include unpaired cases and measure successful-request latency. A grounded answer must contain the expected facts, cite an overlapping, in-bounds range in the expected file, and include a matching source ID and range in the API response. Abstention requires the explicit response requested by the fixture. The rubric is deterministic and deliberately limited to these cases.

The cost estimate uses the Deep model and stored price table in `eval/config.json`. Match the config to the served model before comparing costs. Chat and Debug currently omit usage, which is reported as unavailable. Model-quality floors require repeated live runs. The existing MiniLM retrieval gate has independent floors derived from the measured 36-question baseline.
